# Anti-patterns

PlanGate で避けるべきアンチパターン。各項目は
**Problem / Why it happens / Risk / PlanGate countermeasure** で構成。

## 1. いきなり実装する

- **Problem**: 要求を受けて即コードを書き始める。
- **Why it happens**: 実装が最も「進んでいる感」を出せる。計画は退屈に感じる。
- **Risk**: 要求の誤解釈・既存設計との衝突・手戻り。
- **Countermeasure**: Plan Phase を必須化。Goal / Verification Method が書けるまで Execute に入らない。

## 2. 完了条件なしで作業する

- **Problem**: 「良くなったら終わり」のような曖昧な終端で作業する。
- **Why it happens**: 完了条件の言語化が難しいタスクほど省略される。
- **Risk**: 終わらないループ・過剰実装・「どこまでやったか」不明。
- **Countermeasure**: Intake で観測可能な完了条件を仮置きし、Plan で固定。書けなければ調査タスクに変換。

## 3. 検証方法なしで作業する

- **Problem**: どう確かめるか決めずに変更を加える。
- **Why it happens**: 「動けばわかる」という楽観。検証設計のコストを嫌う。
- **Risk**: 偽の完了・回帰の見逃し。
- **Countermeasure**: 「検証方法を書けない作業は、まだ理解できていない」原則。Plan の必須項目に Verification Method。

## 4. 「たぶん動く」で完了扱いする

- **Problem**: 実行・観測せずに「完了しました」と報告する。
- **Why it happens**: 完了報告への圧力。検証の手間。過去の類似成功の記憶で代用する。
- **Risk**: 偽の完了が下流（レビュー・依存タスク・memory）を汚染する。最も高くつく失敗。
- **Countermeasure**: 完了系は一次証跡で実測後に報告（verify-then-report）。検証結果のない完了は `partial` に格下げ。

## 5. サブエージェントを使うこと自体を目的化する

- **Problem**: 必要性の判断なしに委託し、結果を無検証で採用する。
- **Why it happens**: 「並列＝速い」「委託＝高度」という思い込み。
- **Risk**: トークン浪費・統合コスト・責任の空白（誰も検証していない成果物）。
- **Countermeasure**: 委託前に複雑さ・独立性・並列性を判断。委託しても統合責任者として自ら検証。最終報告に委託の有無と検証結果を明示。

## 6. 既存設計を読まずに新規設計する

- **Problem**: 既存のパターン・命名・責務分離を確認せず「あるべき姿」を新造する。
- **Why it happens**: 読むより書く方が速く感じる。既存への敬意の欠如。
- **Risk**: 二重実装・設計の分裂・レビュー負荷の激増。
- **Countermeasure**: Plan の必須項目に Existing Design Fit。Review で「既存を読んだ証拠」（該当ファイル・該当節の引用）を要求。

## 7. 小さな修正を大規模リファクタに拡大する

- **Problem**: 1 行の修正のついでに周辺を「きれいに」し始める。
- **Why it happens**: 目についた改善点を放置できない。差分の大きさへの無自覚。
- **Risk**: レビュー不能な差分・無関係な回帰・承認境界の無断通過。
- **Countermeasure**: Expected Diff の宣言と実差分の突合（I-9 相当）。宣言外の改善はその場でやらず issue 化。

## 8. 人間承認なしに破壊的変更をする

- **Problem**: 削除・上書き・force 系・本番影響を単独判断で実行する。
- **Why it happens**: 「聞くより謝る方が速い」・承認要否の判定を省略。
- **Risk**: 不可逆な損失。信頼の毀損（最も回復コストが高い）。
- **Countermeasure**: Approval Gate の 11 観点を機械的に通す。迷ったら yes（承認必要）。破棄前に「自分が作った/名指しされた」を確認。

## 9. lint / test / build の失敗を隠す

- **Problem**: 失敗した検証を報告から落とす、または「概ね成功」に丸める。
- **Why it happens**: 失敗報告への心理的コスト。「あとで直すから」の先送り。
- **Risk**: 失敗の発見が下流に遅延し、原因特定コストが増大。
- **Countermeasure**: Verification Report の Failed Checks は 0 件でも「なし」と明記させる（空欄と区別）。失敗を含む報告を正常系として扱う文化。

## 10. 未検証事項を報告しない

- **Problem**: 検証した範囲だけ報告し、検証していない範囲の存在を伝えない。
- **Why it happens**: 「完了」を汚したくない。未検証の列挙は手間。
- **Risk**: 読み手が「全部検証済み」と誤読し、残リスクが無管理になる。
- **Countermeasure**: Skipped Checks / Manual Verification / Remaining Risks をテンプレート必須欄にする。「検証した範囲の境界」を明示。

## 11. 却下した案と理由を memory に残さない

- **Problem**: 採用案だけ記録し、検討の過程を捨てる。
- **Why it happens**: 却下案は「無駄だったもの」に見える。
- **Risk**: 次のセッションが同じ案を再検討・再提案する（無限ループ）。
- **Countermeasure**: plan-memory の Rejected Options / Rejection Reasons を必須欄に。却下履歴は追記のみ（消さない）。

## 12. /compact 後に同じ失敗を繰り返す

- **Problem**: 文脈圧縮で却下理由・計画状態・未解決リスクが落ち、同じ調査・同じ失敗をやり直す。
- **Why it happens**: 記憶をコンテキストにだけ置き、永続層に書いていない。
- **Risk**: 進捗の巻き戻り。ユーザーから見た「学習しない AI」。
- **Countermeasure**: /compact 前の plan-memory 更新を必須化（例プロンプト 9）。セッション開始時に memory を最初に読む。

## 13. 長すぎるプロンプトでモデルの判断能力を潰す

- **Problem**: あらゆるルール・全履歴を詰め込み、肝心の判断材料が埋没する。
- **Why it happens**: 「渡しておけば安心」という保険心理。取捨選択のコスト回避。
- **Risk**: 指示の相互矛盾・重要制約の見落とし・トークン浪費。
- **Countermeasure**: Context Engineering の原則「次の判断に効く情報だけを残す」。委託プロンプトは必須要素（役割・SSOT・既知の事実・却下済み仮説・制約・出力形式）に絞る。

## 14. 宣言と実態の乖離を放置する（偽 DONE）

- **Problem**: ドキュメント上「完了・適用済み」だが実体が伴わない状態を検出しても直さない。
- **Why it happens**: 「書類上は終わっている」ものを再開するコスト。責任の曖昧さ。
- **Risk**: 後続の全判断が誤った前提の上に積まれる（Shadow Configuration）。
- **Countermeasure**: 宣言と実態の突合を定期監査に含める。乖離を見つけたら最優先（P0）で是正し、どちらが正か（実態に合わせるか、適用を完了させるか）を明示的に決める。
