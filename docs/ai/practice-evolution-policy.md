# Practice Evolution Policy — 実践知と外部知識から自分たちの最適解を探す

> **Status**: Living / Proposal v0.1（運用で検証しながら育てる基本方針）
> **Owner**: Maintainer / Human decision owner
> **Recorded**: 2026-10-10
> **Review**: 実践からの重要な学びが出た時／月次の振り返りで必要性を確認
> **Nature**: **価値観と意思決定のガイド。新しい実行契約、Gate、強制チェックリストではない。**

## 1. 私たちの基本姿勢

> **自分たちの事実と経験から考え、一般的な知識や定石と照合する。車輪の再発明は避けるが、流行やベストプラクティスを無批判に導入しない。試し、学び、必要なら自分たちの前提も変える。**

PlanGateで生まれた実装、失敗、成功、開発とアジャイルの知見は重要な資産。一方、その経験だけで正しさを保証しない。研究、標準、OSS、他チームの実践、批判的なレビューを参照し、**異なる観点がぶつかった時こそ検証の機会**とみなす。

ここでの「最適解」は普遍的なベストプラクティスではなく、**現在の課題・制約・チーム・リスクの下で、価値とEvidenceが示す暫定的な選択**である。将来の再評価を歓迎する。

### アジャイル宣言への立脚

私たちは[アジャイルソフトウェア開発宣言（公式日本語版）](https://agilemanifesto.org/iso/ja/manifesto.html)の4つの価値を重視する。プロセスやツール、文書、契約、計画にも価値を認めながら、**個人と対話、動くソフトウェア、顧客との協調、変化への対応をより重視する**。

AIエージェントやOSSの運用では、これを次のように適用する。以下は**私たちの適用解釈**であり、宣言の文言そのものではない。

| 宣言の価値 | PlanGateでの判断の方向 |
| --- | --- |
| 個人と対話 | AIの定型手順やツールの都合より、関係者の意図・文脈・対話を重視。人間の主体性を失わない |
| 動くソフトウェア | 文書だけで完了を主張せず、実際に動作・検証できる小さな成果、または運用上の確認可能な変化を優先 |
| 顧客との協調 | 初期仕様の字面に固執せず、価値・不確実性・変更理由を依頼者と確認する |
| 変化への対応 | 計画は重要な仮説。新しい事実を得たら見直す。ただし承認された境界の外に独断で進まない |

[アジャイル宣言の背後にある原則](https://agilemanifesto.org/iso/ja/principles.html)の、短い間隔での価値提供、技術的卓越性、シンプルさ、自己組織化、定期的な振り返りも参考にする。宣言は**思考の羅針盤**であり、このファイルの一文を実装の通過条件に機械変換するものではない。

## 2. 大切にする価値と、変化させる仕組み

| 層 | 何を扱うか | 変更の姿勢 |
| --- | --- | --- |
| **Values / Principles** | 対話、価値ある成果、協調、変化への対応、観測事実への誠実さ、学び続ける姿勢 | 日々の効率都合で軽々しく手放さない。原則間の緊張は明示し、価値の解釈は経験に照らして深める |
| **Safety / Authority Invariants** | C-3/C-4・HO・Human-owned judgment、秘匿情報、不可逆な危害の防止、証拠と判断の分離 | AIの自己判断・自動改善で緩和しない。変更が必要なら既存のHuman-owned方針策定・承認手続きで明示的に判断 |
| **Policies / Decisions** | 承認済みの対象範囲、役割と責務、品質・安全性・運用上の決定 | 証拠と責任者を明示し、所管する正本を変更して進化させる。基本方針だけで既存決定を上書きしない |
| **Practices / Tools / Workflow** | 手順、バッチサイズ、会議、レビュー方法、モデル、Skill/Agent、計測方法 | 仮説として小さく試し、Keep / Adapt / Revert / Defer を判断する |
| **Evidence / History** | 観測、実測、外部の出典、失敗、代替案、当時の判断根拠 | 履歴を都合よく改ざんしない。新しい評価は追記し、現行方針へのリンクを保つ |

「変えてはいけない」は**価値を否定するような便宜的な変更をAIが勝手にしない**という運用上の意味。人間の正式な方針変更まで永久に禁止する意味ではない。

## 3. 外部の知識と私たちの実績を突き合わせる

次の二つを**別の情報源**として取り扱い、どちらかを最初から正解とみなさない。

- **Local Evidence**: リポジトリの実装・テスト・Issue・PR・実行ログ、運用指標、当事者の経験・観測。経験談は価値があるが、未検証の報告と測定済みの事実を区別する。
- **External Knowledge**: アジャイル、リーン、ソフトウェア工学、論文、標準、公式ドキュメント、他のOSS、他チームの事例。**原典・適用条件・限界・新しさ**を確認し、知名度や流行で判断しない。

実際の検討では以下の順に問いを立てる。ただし**必要な問いだけ**を使い、全項目の書面提出や長い事前審査は要求しない。

1. **Problem / Outcome**: 今、何に困っているか。どんな価値・結果を変えたいか。
2. **As-is / Evidence**: 実際には何が起きているか。観測・報告・推論・未確認を区別できているか。
3. **External insight / Fit**: 一般的な知見はどの条件で成立したか。私たちと何が同じで、何が違うか。
4. **Alternatives / Trade-offs**: 今のやり方の維持、既存知識の採用、適応、試行、見送りにどんなコスト・リスクがあるか。
5. **Smallest useful verification**: 最初にどれだけ小さく試せるか。成功・悪化・停止・切り戻しはどう判断するか。
6. **Evidence → Judgment → Adapt**: 観測の質を確認したうえで、採用・修正・撤回・保留を決める。Evidenceそのものを承認や権限に昇格させない。

### 知識との向き合い方 — 4つの選択

| 選択 | いつ選ぶか | 例 |
| --- | --- | --- |
| **Adopt（採用）** | 条件が十分近く、現状に必要で、導入価値・安全性が確認できる | 実在する重複IssueのGitHub標準Duplicate機能 |
| **Adapt（適応）** | 原則は有効だが、私たちの役割・制約・承認境界に合わせた再設計が必要 | Agileの短いフィードバックを3〜5件のTriageバッチへ翻訳 |
| **Transform（自分たちを変える）** | 自分たちの前提・分業・評価指標が障害で、変革が価値を生む仮説がある | 「Open件数を減らせば成功」という見方を捨て、正しい判断・回復の質を測る |
| **Defer / Reject（見送り）** | 適合しない、必要性が薄い、危険または証拠不足。無理に導入しない | 新たなstale bot/強制Gateを、問題の実測なしに追加すること |

**Adoptが上位、Deferが下位という序列ではない。** 何もしないことも合理的な判断。Transformも変化そのものを目的化せず、小さな実験と人間の判断に支えられる。

## 4. Fast Feedback / Quick Recoveryを実務へ

- **価値を最小スライスで示す**: 完璧な文書や制度設計を待たず、既存のツール・フローで確認できる実験から始める。
- **失敗が見えるようにする**: テスト、負の検証、ログ、再取得、実利用者からのフィードバック。品質を証明できないgreenを成功としない。
- **戻せる範囲で速く動く**: 可逆性・影響範囲・変更の粒度を選ぶ。不可逆・セキュリティ・Human権限に関わる判断は先に停止条件を満たす。
- **対話を後回しにしない**: 不確実性が重要なときは依頼者・責任者に早く共有する。対話することと、決定権をAIに移すことは別。
- **改善を増やしすぎない**: 既存の仕組みをまず試し、ルール、Gate、Skill、Agent、ダッシュボードは効果が確認できて初めて候補にする。

## 5. Discovery / Delivery / Process Evolutionの関係

- **Discovery**: 何を、なぜ変えるべきかを探索し、証拠を集め、必要性とリスクを検証する。
- **Delivery**: 判断された変更を小さく実行・検証・提供する。Discoveryと継続的に対話する。
- **Process Evolution**: DiscoveryとDeliveryの結果から、**やり方自体**の改善仮説を作り検証する。必要なら「何を成果とするか」という前提も問い直す。

Dual Track（Discovery / Deliveryの並走）と、Issue Triage / Process Evolutionという**活動とその方法の改善**は同じ意味ではない。Double-Loop Learningも、単にループが2つある状態ではなく、規範・目的・前提を問い直す学習を指す。

具体例と議論の経緯は [PR #1548](https://github.com/s977043/PlanGate/pull/1548) の設計履歴および [Issue #1503](https://github.com/s977043/PlanGate/issues/1503) を参照する。これは実装済みの組織制度の宣言ではなく、**考え方を運用へ適用するためのガイド**。

## 6. 記録と振り返り（軽量に）

重要な知識の取り込みや方針変更では、Issue / PR / 既存のDecision Recordに最低限、次の材料を残せばよい。軽微な対応までテンプレートを強制しない。

```text
Problem / observed facts:
External insight / original source / limits:
Fit & gap with our context:
Options: Adopt / Adapt / Transform / Defer (why):
Small experiment / evidence / stop & rollback:
Decision / owner / remaining unknowns:
Revisit trigger:
```

- **少なくとも一度、別視点で問い直す**: 「既存知識を無批判にコピーしていないか」「独自性に固執して車輪を再発明していないか」「品質や承認境界を弱めないか」。独立レビューの実施要否と強度は既存のモード・リスク判断に従う。
- **小さく試す → 観測 → 振り返る**: 成功と失敗を記録。ルールを増やすより、不要な手順を減らす改善も歓迎する。
- **再訪条件を持つ**: 適用条件、証拠の鮮度、コスト、プロダクトの変化が生じたら再検討する。
- **履歴と現行方針を分ける**: 議論・決定の理由は保持し、現行ルールだけを各正本で更新する。過去の見解が変わった場合も当時の事実を消さず後続の判断を追記する。

### 例: Issue管理での適用

「OSSのIssueは古いものを自動Closeするのが効率的」という一般論があった場合:

- Local Evidence: 現行実装、古いissue、継続リスク、未達ACを確認する
- External Knowledge: GitHubのClose reasonやDuplicate機能、stale運用事例を調べる
- Choice: 一律の自動Closeは **Defer**。安全な小バッチの分類と相互リンクは **Adapt**
- Experiment: 3〜5件を試行し、誤Close・未移管AC・回復所要時間を確認する
- Evolve: 「Close件数が多いほど良い」という前提が実態に合わなければ **Transform** の候補とする

この例は**考え方の適用例**であり、全Issueの棚卸しが完了したという実績ではない。

## 8. 改訂の考え方

- この文書は完成品ではない。現場の観測・失敗・新しい外部知識により、**判断の説明力と有効性**を高める。
- 変更内容が **実行契約・承認・セキュリティ** に及ぶなら、その変更をAIが黙って適用しない。既存正本と承認経路に従う。
- 外部に記事化する際は **原典の知識／私たちの解釈／未検証仮説／実測済みの結果** を分ける。失敗の歴史を含め、追えるリンクを保持する。
- この文書の運用価値が薄ければ、文書や会議体を増やすのではなく、内容を既存の必要なガイドへ統合する選択も許す。
