## 1. 実測 — `ta-62` は何回実行されるか

**数え方**: `ta-62` の `pg_extra_contract_init` 直後に「呼ばれたら 1 行追記する」
カウンタを一時的に仕込み（`PG_T62_COUNT_FILE`）、フルスイートを 1 回完走させて
行数を数えた。sandbox 複製経路も `git ls-files -c -o` でコピーされるため同じ
カウンタファイルに記録される。**推測ではなく実測。**

| 実行モード | 実行ディレクトリ | 回数 |
|---|---|---|
| harness（`run-tests.sh` から source） | 実 `tests/extras` | **1** |
| standalone（`ta-61` per-file ループ: stage-1 clean / force-fail probe / contaminated env） | 実 `tests/extras` | **3** |
| standalone（`ta-61` TC-16 が起動する sandbox 複製の `ta-61` の同ループ） | `/var/folders/.../sandbox/repo/tests/extras` | **3** |
| | **合計** | **7** |

→ **issue 本文の「7 回」は実測で正しい。** 内訳も issue の記述と一致する。

構造上の原因は `tests/extras/ta-61-extra-contract.sh` の
`_T61_STANDALONE_LIST` を回すループで、`standalone-capable` の各ファイルを
**1 ファイルにつき 3 プロセス**起動する（TC-12(a)/TC-13、TC-12(b)、TC-15）。
`ta-62` が `standalone-capable` を宣言しているため、この 3 倍がそのまま乗る。
さらに TC-16 が repo を sandbox へ丸ごと複製して `ta-61` 自身を再実行するため、
同じ 3 倍がもう一組増える。

### 2-3. `ta-62` の内訳 — 何が遅いのか

`ta-62` の TC は 2 つだけ:

| TC | 内容 | コスト |
|---|---|---|
| TC-S | `grep` / `awk` による静的配置検査 | ほぼ 0 |
| TC-D | ミニ harness ドライバで **`ta-26` を leak / clean の 2 回 source** | **ほぼ 100%** |

→ **`ta-62` の所要はほぼ「`ta-26` 2 本ぶん」**（序盤実測: ta-26 単体 50/50/68 秒、
ta-62 89 秒 ≒ 2 × 44 秒）。

`ta-26` 側の内訳（出力行にタイムスタンプを打って TC 間の差分を取った実測、
上位のみ・合計 ≈ 44 秒）:

| TC | 秒 | 内容 |
|---|---|---|
| **TC-13** | **20.1** | `ta-26` 自身を子プロセスとして **2 回**起動（素 / `FIXTURES_DIR` 汚染） |
| TC-05 | 6.4 | repo を sandbox へコピーして実 sync を実行 |
| TC-04 | 5.9 | 実 repo に対する `--dry-run` + plugin 全ファイルのハッシュ |
| TC-03 | 5.6 | 実 repo に対する `--dry-run` |
| 残り 28 TC | 合計 ≈ 6 | `mktemp -d` ベースの小さな guard sandbox 群 |

**つまり最深部のコスト源は `ta-26` TC-13 の孫プロセス起動である。**
`ta-62` 1 本 = `ta-26` 2 本 = さらにその中で `ta-26` の孫が 4 本走る。
これが 7 回繰り返されている。

### (c) の結論: **削れない**

TC-D は「`PG_T26_NO_RECURSE` が漏れた実行」と「漏れていない実行」の
**差分検査**であり、構造上 2 本必要。1 本にすると検査そのものが消える。
各 1 本を安くする道は 2 つあるが、いずれも採れない:

1. **`ta-26` 側を軽くする** — `ta-62` の検査対象そのものを変えることになる。
   加えて TC-D は `ta-26` の**出力全体の diff 完全一致**を見ており、これは
   「将来 `ta-26` に `PG_T26_NO_RECURSE` 感応の TC が増えても自動追従する」
   ための設計。出力を絞ると**その追従性（＝将来の検出力）を落とす**。
2. **2 本を並列化する** — 壁時計時間は理屈上ほぼ半減するが、
   (i) 2 コアの ubuntu-latest ではほぼ効かない、
   (ii) **両者が競合して 1 本あたりの所要が伸び、§5 の 180 秒 per-run 上限に
   より近づく**（本セッションで実際に発火した経路）。
   削減 40 秒級のために flake 要因を足す取引になるため**非推奨**。

→ **(c) は「検出力を落とさずには実現できない」が結論。** 実装しない。

## 4. 推奨

**(a) を第一候補として Human 裁定にかける。** 理由:

1. **効果が桁違い**。実行回数 7 → 1 は決定論的に確認済みで、`ta-62` の
   スイート寄与の 86% を消す。他のどの案もゼロ〜数十秒級でしかない。
2. **`ta-62` 自身の検出力を 1 ミリも落とさない**。`ta-62` が守っているのは
   「`PG_T26_NO_RECURSE` が呼び出し元 env から漏れると `ta-26` の TC 群が
   黙って `[SKIP]` で消える」という回帰であり、その検査（TC-S / TC-D）は
   **harness 経路でこそ意味を持つ**。standalone 実行は検査の付随物にすぎない。
3. **分類として素直**。`ta-62` はファイル冒頭に自ら
   「Sourced by tests/run-tests.sh」と書いており、TC-D は harness 環境を
   自前で再現するミニドライバを組み立てている。**主題が harness 経路**である。
4. **`ta-61` 側の被覆は差し引きゼロに近い**。失う 3 種の契約検査は
   他の 20 数ファイルで引き続き掛かっており（`ta-61` TC-25(1)/(3) が
   非空性を機械保証）、代わりに **現在 vacuous な TC-11 が非 vacuous になる**。

**ただし正式採用は Human 裁定が必要**（§6）。

(b) は**単独では何も解決しない**（実行時間は不変）。(a) 採用後もローカル
19 分・CI 10 分キャップという事実は残るため、**(a) と (b) は排他ではなく、
(a) で削ったうえで (b) の余裕幅を Human が判断する**のが妥当。

## 5. 副次的に発見した独立の CI-red リスク（本 PBI で診断のみ是正）

案 (a) の試作実走で **TC-D が FAIL** した:

```
[FAIL] TC-D 同値照合不成立 (rc_leak=0 rc_clean=142 期待0/0 / diff一致=0 ...)
```

`142` は `perl -e 'alarm ...'` の SIGALRM、すなわち**ドライバ 1 本が
per-run 上限 180 秒を超えた**という意味である。案 (a) の変更は `ta-62` の
本体を一切触らないので、**これは (a) が起こした失敗ではなく、元から存在した
脆さが環境劣化で顕在化したもの**。

- セッション序盤: ドライバ 1 本 ≈ 44 秒（上限まで 4 倍の余裕）
- セッション終盤: `ta-62` 全体 215 秒 → ドライバ 1 本 100 秒超
- 実際に 180 秒を突破して発火

**2 コアの ubuntu-latest ではこの余裕はさらに薄い。** `ta-62` は
「遅いマシンで意味不明な赤を出す」テストになっている。

さらに悪いことに、**打ち切られた側の出力は途中で切れるため diff は必ず
不一致になり、素のメッセージは「`ta-26` の出力が leak/clean で食い違った」
という誤った診断を出す**。実際、上の FAIL メッセージの diff 断片は
「clean 側に TC-05〜TC-13 が無い」ように見え、`rc_clean=142` を読まなければ
env guard の回帰と誤読する。

### 本 PBI での是正（実装済み・検出力不変）

`tests/extras/ta-62-t26-recurse-env-guard.sh`:

- `rc` が `124`(timeout(1)) / `142`(SIGALRM) のときは**同値照合の前に切り分け**、
  「TIMED OUT」と明示する専用の FAIL を出す。**FAIL のまま**であり
  `[SKIP]` に逃がさない（`ta-61` TC-12 の既存文言と同型）。
- per-run 上限を `_T62_TIMEOUT` 変数に括り出し、メッセージにも同じ値を使う
  （数値のハードコード二重管理を除去）。

**assertion は 1 つも変えていない**ので検出力は不変。
変異注入で検証済み（`_T62_TIMEOUT=1` に落として新分岐の発火を実物確認 →
旧実装なら誤診断メッセージが出る経路が、新分岐で正しい診断に変わることを確認）。

**現レートでの余裕幅（対照実験より）**: `ta-62` 1 本 207 秒 = ドライバ 1 レッグ
約 103 秒。per-run 上限 180 秒に対し**余裕はわずか 1.75 倍**しかない。
セッション序盤（44 秒 / 余裕 4 倍）から大きく縮んでいる。

### Human 判断が要る残件

`_T62_TIMEOUT` の**値そのもの**（180 秒が妥当か）は本 PBI では変更していない。
上げれば flake 耐性が上がるがハング時の待ち時間が伸びる、というトレードオフで
判断が要るため。**(a) を採用すると `ta-62` の実行が 7 → 1 に減り、マシン負荷も
下がるので、この問題の発生確率自体が下がる**点も併せて判断されたい。
