### `release-prep.sh --check` の既知 NG 2 件（本リリースの阻害要因ではない）

## 6. ロールバック手順（parity 不一致時）

Step 5 が `MISMATCH` を返した場合、**GitHub Release を作成せず**に tag を貼り替える。
正本: [`docs/release-process.md`](../../release-process.md) §失敗時のフロー (MISMATCH 検出時)。

1. **リモート tag オブジェクトの SHA を取得する**（`--force-with-lease` の期待値に使う）

   ```sh
   git ls-remote --tags origin refs/tags/v8.22.0
   ```

   > annotated tag では ref の格納値が **tag オブジェクト**の SHA であり、peel 先の commit SHA を
   > 期待値にすると必ず stale info で拒否される（R-002）。使うのは `refs/tags/v8.22.0` の
   > **un-peeled 行**（`^{}` が付かない行）の SHA

2. **ローカル tag を貼り替える**

   ```sh
   git tag -f -a v8.22.0 -m "release v8.22.0" $(git rev-parse origin/main)
   ```

3. **`--force-with-lease` + ref 明示で push する**（`<リモート tag オブジェクト SHA>` は 1 で取得した値）

   ```sh
   git push --force-with-lease=refs/tags/v8.22.0:<リモート tag オブジェクト SHA> origin refs/tags/v8.22.0
   ```

   > `MISMATCH` 時は `scripts/check-tag-main-parity.sh` が上記コマンドを実測値入りで出力する。
   > **裸の `--force` は使わない**（他者の push を黙って上書きするため）

4. **一致するまで再検証する**

   ```sh
   sh scripts/check-tag-main-parity.sh v8.22.0
   ```

`OK` になるまで 1〜4 を繰り返す。**`OK` を見ずに Step 6 へ進んではならない。**

### 7-2. plugin consumer 側への反映 👤 Human（ローカル専用）

```sh
claude plugin marketplace update plangate
```

```sh
claude plugin update plangate@plangate
```

> - `claude plugin update plangate`（marketplace 名なし）は `Plugin "plangate" not found` で失敗する。
>   `plangate@plangate` が正しい引数
> - 更新の反映には **Claude Code の再起動が必要**

>   `release-prep.sh --check` に version bump ゲートを配線した理由であり、本リリースでは
>   `8.22.0` へ bump 済み（§4 Step 1 で実測確認）
