## 1. semver 裁定の記録（規約との食い違い）

**結論: 本リリースは `8.19.0`（minor）で出す。ただし自 SSOT と食い違った状態が残る。**

### 規約に照らした材料（major 側）

[`docs/ai/versioning-stability-policy.md`](../../ai/versioning-stability-policy.md) §2.2 は Enforcement Hook について次を定める:

| 変更 | severity |
|---|---|
| 既定挙動の変更（warning → block、**SKIP → BLOCK** 等） | **major** |
| 新規 hook の追加（既定 ON / 強制） | **major** |
| 新規 hook の追加（既定 OFF / opt-in） | minor |

本リリースの `15b0c16`（#1023 / #1042）は EH-13（`scripts/check-approval-token-write.sh`）に対し以下を行っており、**上表 1 行目に該当する**:

1. block の終了コードを `exit 1` → **`exit 2`**。PreToolUse で block として扱われるのは `2` のみで、`exit 1` は非 block。**つまり従来は検出しても止めていなかったものが、本リリースから止まる**
2. `jq` 不在 / 空 stdin / TTY / read error / malformed payload / 未知 tool を **parse-unknown として fail-closed（`exit 2`）**。従来はいずれも素通りだった
3. EH-13 は `.claude/settings.example.json` の **PreToolUse（層 A・常時発火）に配線済み**であり、opt-in ではない

EH-12（#967 / #985）は `settings.example.json` に同梱されるが、実環境での有効化は `scripts/apply-eh-git-destructive-guard.sh --apply`（Human-owned）を要するため opt-in 寄り = minor 材料。ただし `settings.example.json` を素で取り込む導入先では既定 ON になる。

### 裁定

- **判定者**: Human（2026-08-13）
- **裁定内容**: 「**8.19.0（minor）と考えてます**」
- **経路**: AI が §2.2 に照らして major の材料を提示 → Human が minor と裁定。**規約を書き換えて辻褄を合わせることはしていない**（規約改定は本リリースの越権）

### 残る不整合（意図的に残す）

> **`docs/ai/versioning-stability-policy.md` §2.2 の判定（major）と、v8.19.0 の実際の採番（minor）は食い違っている。**

この乖離は次のいずれかで解消されるべき follow-up として残る:

1. §2.2 に「セキュリティ方向の fail-closed 化は minor で許容し、CHANGELOG で `[MIGRATION REQUIRED]` を必須にする」といった例外条項を設ける（規約改定 PBI）
2. 例外を設けず、以後この種の変更は major で出す（本件を一度きりの裁定として扱う）

**緩和措置として実施したこと**: CHANGELOG の v8.19.0 エントリ冒頭に専用の警告節「⚠️ 更新前に必ずお読みください（EH-13 の挙動変更）」を設け、`[MIGRATION REQUIRED]` タグ（policy §4 の正規記法。CHANGELOG での初使用）を Fixed の当該エントリに付与した。

## 3. リリース手順

各ステップの担当を明記する。**AI は #1〜#6 の bump と CHANGELOG 整備・コマンド提示まで。tag push / Release 作成は Human-owned。**

### Step 1: 準備 PR のマージ 👤 Human

`chore/release-8.19.0` の PR を作成・レビュー（C-4）・main へマージする。

```sh
# マージ後、ローカルを main の最新に合わせる
git checkout main && git pull --ff-only origin main
git rev-parse origin/main   # 以降のステップで使う SHA
```

### Step 2: `CLAUDE.md`「最新リリース」節の適用 👤 Human（HO パス）

`CLAUDE.md` は Hardening Override 対象のため **AI は編集できない**。過去リリースと同様、`scripts/apply-claude-md-v81*.sh` 方式（`scripts/` 直下 = HO 外の apply スクリプトを AI が作成し、Human が `--apply`）を踏襲する。

**本リリースでは apply スクリプト（`scripts/apply-claude-md-v8190.sh`）は未作成**。以下のいずれかで対応する:

- (a) AI に `scripts/apply-claude-md-v8190.sh` を作成させ、Human が `sh scripts/apply-claude-md-v8190.sh --apply` を実行（過去 3 世代と同じ方式・推奨）
- (b) Human が `CLAUDE.md` を直接編集

置き換える節の推奨文面（`## v8.18.0 実 PR 収束（MERGE_READY）の一気通貫（最新リリース機能）` 見出しごと差し替え）:

```markdown
## v8.19.0 承認境界ガードの fail-closed 化（最新リリース機能）

> 最新リリース: **v8.19.0**（2026-08-13）v8.18.0 タグ以降に main へ蓄積した 65 マージ（+65.5k 行）を反映。主要変更: **EH-13 承認トークン書き込みガードの fail-closed 化**（#1023/#1042。block を exit 1 → **exit 2**・stdin 常時独立評価・jq 不在 / malformed を parse-unknown として block。**`jq` が実質必須**）・**EH-12 protected branch 上の破壊的 git 操作ガード**（#967/#985。配線は `scripts/apply-eh-git-destructive-guard.sh --apply` = Human-owned）・**tests/extras 共有 exit 契約**による「静かに通る失敗」の封鎖（#921 Slice 1 / #1046）・**plugin skill 参照解決の 3 段フォールバック化**（#954 系。Codex 経由導入で解決不能だった相対リンクを是正）。**PlanGate 本番フロー WF-00〜07 は不変・NO MERGE BY AI／C-4・merge は Human-owned 固定**。リリース履歴の正本は [`CHANGELOG.md`](CHANGELOG.md)。
```

> ⚠️ **AI は apply スクリプトを作成するだけで、`--apply` は実行しない**（HO 適用は Human-owned）。

### Step 3: annotated tag の作成 👤 Human

```sh
# 現在地が main の最新であることを確認してから打つ
[ "$(git rev-parse --abbrev-ref HEAD)" = "main" ] || { echo "ABORT: not on main"; exit 1; }
git fetch origin main
[ "$(git rev-parse HEAD)" = "$(git rev-parse origin/main)" ] || { echo "ABORT: HEAD != origin/main"; exit 1; }

git tag -a v8.19.0 -m "release v8.19.0"
```

### Step 4: tag の push 👤 **Human**

```sh
git push origin v8.19.0
```

### Step 5: 🚪 Iron Law — TAG-MAIN PARITY 検証 👤 Human（**Release 作成前に必須**）

```sh
sh scripts/check-tag-main-parity.sh v8.19.0
```

- `OK: tag 'v8.19.0' (origin 実体) = origin/main (<sha>)` → **Step 6 へ進んでよい**
- `MISMATCH` / `FAIL` → **GitHub Release を作成してはならない**。[`docs/release-process.md`](../../release-process.md) §失敗時のフロー に従って `--force-with-lease=refs/tags/v8.19.0:<リモート tag オブジェクト SHA>` で貼り替え、**一致するまで再検証**する（MISMATCH 時は script がそのコマンドを出力する）
- 実行ログは本手順書または release note に貼って記録する

### Step 6: GitHub Release の発行 👤 **Human**（Step 5 が OK になるまで実行しない）

```sh
gh release create v8.19.0 \
  --title "v8.19.0 — 承認境界ガードの fail-closed 化（EH-13）+ 破壊的 git 操作ガード（EH-12）" \
  --notes-file docs/working/_reports/v8.19.0-release-note.md
```

> `--notes-file` に渡す release note は **CHANGELOG の v8.19.0 節をそのまま流用してよい**（特に「⚠️ 更新前に必ずお読みください」節は Release 本文に必ず含めること）。note ファイルの用意は AI-owned。

### Step 7: リリース後の workflow run 結果確認 👤 Human（#950）

`release-docs-sync` は release published 起点で動くが、**失敗しても通知されない**。v8.17.0 / v8.17.1 / v8.18.0 で 3 連続失敗し `docs/changelog.md` が 2 世代欠落した実績があるため、必ず確認する。

```sh

gh run list --workflow=release-docs-sync.yml --event=release --limit 1
```

- `conclusion = success` → 完了（version 同期マップ #8 が自動 PR で満たされる）
- `conclusion = failure` → [`docs/release-process.md`](../../release-process.md) §失敗時のリカバリ に従い、push 済みの `chore/release-docs-sync-<run_id>` ブランチから手動で PR を作成する（`--title` と `--body` を**両方**指定する）

あわせて plugin sync 側も確認する:

```sh

```

## 5. #1045 の実装状況による CHANGELOG の分岐

**#1045（EH-13 が `2>/dev/null` / `2>&1` / `>&2` を書き込みと誤判定し、読み取り専用コマンドを block する）はリリース前に exec する方針**（別ワーカーへ委託済み）。CHANGELOG は **「#1045 が入らない」前提で執筆済み**のため、**入った場合は以下 2 箇所を差し替える**こと。

### 差し替え箇所 A: `### Notes（既知課題）` の 2 番目の項目 — **削除する**

現在の記述（#1045 が入らない場合はこのまま）:

> - **#1045（EH-13 の読み取り誤 block）** — `2>/dev/null` / `2>&1` / `>&2` は fd 複製・破棄であってファイル書き込みではないが、`_has_write_intent()` が `>` を 1 文字でも含めば書き込みと判定するため、**承認トークンのパス名を含む純粋な読み取りコマンドが block される**（例: `grep -c '<token path>' .gitignore 2>/dev/null` / `cat <token path> 2>/dev/null` が `exit 2`）。回避策は当該コマンドから stderr リダイレクトを外すこと

**#1045 が入る場合はこの項目ごと削除**し、代わりに 差し替え箇所 B を `### Fixed` へ追加する。

### 差し替え箇所 B: `### Fixed` へ追加する項目（#1045 が入る場合のみ）

```markdown
- **EH-13 の読み取り誤 block を解消**（#1045）— `2>/dev/null` / `2>&1` / `>&2` は fd 複製・破棄であってファイルへの書き込みではないため、書き込み意図の判定から除外した。従来は `>` を 1 文字でも含めば書き込みと判定していたため、承認トークンのパス名を含む**純粋な読み取りコマンドが block されていた**（`grep -c '<token path>' .gitignore 2>/dev/null` / `cat <token path> 2>/dev/null` が `exit 2`）。実ファイルへのリダイレクト（`> <token path>` / `>> <token path>`）の block は維持
```

### 差し替え箇所 C: 「⚠️ 更新前に必ずお読みください」節 — **どちらの場合も変更しない**

`jq` 必須化 / `exit 1` → `exit 2` / 検出範囲の拡大は **#1045 の有無にかかわらず発生する**ため、この節は不変。

> **注意**: #1045 の実装が `_has_write_intent()` を変更する場合、`tests/extras/ta-25-approval-token-guard.sh` の期待値も更新される。リリース前に `sh scripts/run-tests-safe.sh` を通すこと。
