## 2. 実行時間 — 是正前は非線形（判定保留の原因）

`_pg_fold_tolower` の 1 文字ループは `${v#?}` と `${v%"$rest"}` が毎回全長を走査する
ため、入力長 n に対して O(n^2)。**セグメント上限 256 は「セグメント数」しか見ておらず
総文字数を制限しない**ので、`1 セグメント x 20,000 文字` は上限判定を通過して
写像ループだけが回る。**EH-3 に `timeout` は無い**ため、暴走は block ではなく
**ハング**になる＝可用性の穴。

### 是正前 / 是正後（同一ハーネス・同一セッション）

計測は `_pg_fold_path "$path" "/Users/user/repo" 1` を 1 回。前後に `python3` を
起動して時刻を取るため、**各行に ~50〜60ms の固定オーバーヘッドを含む**
（`CLAUDE.md` の行がそのオーバーヘッドの目安）。

## 3. 是正の内容

1. **小文字化を `/` セグメント単位に分割**（出力は分割しない場合と byte 一致）。
   コストが「全長の 2 乗」から「各セグメント長の 2 乗の総和」になる。
2. **fail-closed に 2 条件を追加**:
   - (c) 全体長 > `_PG_FOLD_MAXLEN=4096`（PATH_MAX の上限。Linux 4096 / macOS 1024）
   - (d) セグメント長 > `_PG_FOLD_MAXNAME=255`（NAME_MAX。macOS / Linux とも 255）

   1 だけでは `1 セグメント × 20,000 文字` が残り、2 だけでは worst case が
   数十秒に達する。**両方が要る**。

### 判定: 受容ではなく**是正**（plan からの逸脱を伴う）

- **AC-8 は fail-closed を (a)(b) の 2 条件と規定**しており、(c)(d) の追加は
  **plan v4 からの逸脱**。`plan.md` は C-3 承認済みで編集できないため、
  逸脱として `status.md` 計画からの変更点 #9 と `decision-log.jsonl` に記録する。
- **正当な書き込みを止めない**: (c)(d) に該当する入力は PATH_MAX / NAME_MAX を
  超えており、**どの FS 上のファイルも指しえない**（`open(2)` が `ENAMETOOLONG`）。
  したがって block しても既存の運用を壊さない。TC-09b（絶対パスを block しない）
  とも両立する（同 TC の入力はすべて上限内）。
- **却下した代替案**:
  - 「受容する」— 却下。EH-3 に timeout が無く、`Edit`/`Write` が全部止まる
    可用性の穴が残る。「悪意ある入力でのみ発火する」ことは受容の理由にならない。
  - 「セグメント分割のみ」— 却下。`1 セグメント × 20,000 文字` に効かない（実測）。
  - 「HO の `case` を `[Cc][Ll]...` の文字クラスにして小文字化自体をやめる」—
    今回は不採用（V2 候補）。root 除去の大小文字非依存比較が別途必要で、
    195 件の直積 TC と変異 M1〜M10 の作り直しを伴い、セッション終盤の
    再設計リスクが高い。

## 4. 検出力（新条件に対する変異）

| 変異 | 内容 | kill | 検出 TC |

## 5. 残る非機能上の注意

- 上限内の worst case（4095 文字・全大文字）は **~0.5 秒**。ハングではないが
  typical（~50ms）より 1 桁遅い。実運用のパスは 100 文字前後なので影響は無い。
- `ta-65` TC-09c は**上限 120 秒**で外側から切る（`timeout` / `perl alarm`）。
  退行したときに FAIL ではなくハングで CI が詰まるのを防ぐため。
- **実行時間の絶対値は契約値ではない**。TC-09c が見ているのは
  「上限内 worst case が 120 秒以内に終わるか」だけ。
