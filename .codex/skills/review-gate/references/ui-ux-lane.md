# レーン 5: UI/UX・アクセシビリティ — 詳細リファレンス

> `review-gate` Skill レーン 5 の bundled reference（progressive disclosure /
> #797）。SKILL.md 本文には要約チェックリストのみを置き、個別解説・Pass/Fail
> 判定方法・worked example は本ファイルに分離する。
> 出典: growth-core `ui-ux-review` の汎用部（Nielsen 10 + WCAG。LP・CVR 等の
> ドメイン固有評価軸は不採用）+ W3C「What's New in WCAG 2.2」。

## 1. 発火判定の詳細

### 1.1 機械可読ヒューリスティック（例示リスト）

差分に以下の UI 系パス・拡張子を **1 つでも含む**場合、レーン 5 を発火する。
これは例示であり、プロジェクトの UI 層構成（フレームワーク・ディレクトリ命名）
に応じて読み替える:

| 軸 | パターン例 |
|----|-----------|
| 拡張子 | `*.css` / `*.scss` / `*.sass` / `*.less` / `*.vue` / `*.tsx` / `*.jsx` / `*.svelte` / `*.astro` / `*.blade.php` / `*.erb` / `*.twig` / `*.html` |
| パス | `components/**` / `views/**` / `templates/**` / `pages/**` / `layouts/**` / `styles/**` |

### 1.2 安全側規則（曖昧時は発火側に倒す）

UI 変更か否かが曖昧な場合（例: `*.ts` だが DOM 操作・style 注入を含む、
サーバーサイドだがレンダリング HTML を組み立てる）は**発火側に倒す**。
`mode-classification.md` 変更種別軸の「境界が曖昧なら上位種別として扱う」と
同型の安全側規則であり、「UI ではない」ことを証明できるときだけスキップする。

### 1.3 入力可用性条項

スクリーンショット / プレビュー URL / Figma 等の視覚入力がレビュー入力に
無い場合、**黙ってスキップしない**。次のいずれかを行う:

1. **取得手順の提示**: ローカル起動手順 + スクリーンショット採取コマンド
   （Playwright / ブラウザ devtools 等）を提示し、視覚入力の提供を依頼する
2. **unavailable 記録**: `docs/ai/external-reviewer-interface.md` §10 と同型で
   「実行不可の理由 / 代替レビュー観点（静的コード検査で確認した範囲）/
   未充足リスク」を finding に必須記録する（空欄の unavailable は無効）

## 2. Nielsen 10 ヒューリスティクス（個別解説）

| # | ヒューリスティック | 解説・チェック方法 |
|---|------------------|------------------|
| 1 | **システム状態の可視性** | 処理中インジケータ・保存完了・現在地（パンくず・アクティブタブ）が適時フィードバックされるか。非同期処理にローディング/完了/失敗の 3 状態表示があるか |
| 2 | **実世界との一致** | ユーザーの言葉・慣習に沿った表現か。DB カラム名・内部 enum 値・例外メッセージをそのまま UI に露出していないか |
| 3 | **ユーザーの主導権と自由** | 取り消し（undo）・キャンセル・戻る導線があるか。モーダルに閉じる手段があるか。破壊的操作から復帰できるか |
| 4 | **一貫性と標準** | 同じ意味に同じラベル・アイコン・配置を使っているか。既存画面のボタン順序（例: キャンセル/実行の並び）・語彙と矛盾していないか |
| 5 | **エラー防止** | 誤操作を起こしにくいか。破壊的操作に確認ステップ・入力に制約（型・範囲）・安全なデフォルト値があるか |
| 6 | **想起より認知** | 記憶に頼らせず選択肢・候補・入力例を見せているか。前画面の情報を覚えていないと操作できない構造になっていないか |
| 7 | **柔軟性と効率** | 熟練者向けショートカット（キーボード操作・一括操作）と初心者向け導線が両立しているか |
| 8 | **美的で最小限のデザイン** | 不要な情報・装飾が主要情報と競合していないか。1 画面の主要アクションが明確か |
| 9 | **エラーの認知・診断・回復支援** | エラーメッセージが平易な言葉で「何が起きたか + どうすれば直るか」を示すか。エラーコードのみの表示になっていないか |
| 10 | **ヘルプとドキュメント** | 必要な場面で文脈に応じたヘルプ（ツールチップ・リンク）へ到達できるか |

## 3. WCAG 必須チェック（Pass/Fail 判定方法）

### 3.1 基本 5 点

| 項目 | 基準 | Pass/Fail 判定方法 |
|------|------|------------------|
| コントラスト | 1.4.3 (AA) | 通常テキスト 4.5:1 以上、大きいテキスト（24px / 太字 18.5px 以上）3:1 以上。devtools のコントラスト表示・axe 等で実測 |
| 代替テキスト | 1.1.1 (A) | 意味を持つ `img` に内容を表す `alt`。装飾画像は `alt=""`。アイコンボタンに accessible name（`aria-label` 等） |
| フォーカス可視 | 2.4.7 (AA) | Tab 移動でフォーカス位置が視認できる。`outline: none` で消して代替表示が無いものは Fail |
| キーボード操作 | 2.1.1 (A) | 全機能がキーボードのみで操作可能。`div` + `onClick` のみでフォーカス不能・Enter 不能なものは Fail |
| フォームラベル | 1.3.1 / 3.3.2 (A) | 入力欄に `label for` / `aria-label` / `aria-labelledby` の関連付け。placeholder のみは Fail |

### 3.2 WCAG 2.2 新基準（A/AA の 6 つ）

| 基準 | レベル | Pass/Fail 判定方法 |
|------|-------|------------------|
| **2.4.11 Focus Not Obscured (Minimum)** | AA | フォーカスした要素が固定ヘッダー・sticky フッター・追従バナーに**完全に**隠れないこと。Tab で全要素を巡回し、フォーカス先が一部でも視認できれば Pass |
| **2.5.7 Dragging Movements** | AA | ドラッグ&ドロップ・スライダー等のドラッグ操作に、クリック/タップ等の単純ポインタ操作の代替（上下ボタン・数値入力・メニュー移動）があれば Pass |
| **2.5.8 Target Size (Minimum)** | AA | クリック/タップターゲットが 24×24 CSS px 以上。未満でも、24px 円が隣接ターゲットと重ならない間隔がある・同等機能の別ターゲットがある・インライン文中リンク等の例外は Pass |
| **3.3.8 Accessible Authentication (Minimum)** | AA | 認証に記憶・転記等の認知テスト（パズル・暗記）を要求しない。パスワード欄のコピー&ペースト・パスワードマネージャの自動入力を妨げなければ Pass |
| **3.2.6 Consistent Help** | A | ヘルプ手段（問い合わせ先・チャット・FAQ リンク）が複数ページで同じ相対位置・順序にあれば Pass |
| **3.3.7 Redundant Entry** | A | 同一プロセス内（例: 複数ステップのフォーム）で一度入力した情報の再入力を求めない。自動入力・選択式での再利用があれば Pass（セキュリティ上の再入力＝パスワード確認等は例外） |

### 3.3 レスポンシブ確認

- 主要ブレークポイント（最低 PC / SP の 2 点。プロジェクト定義があればそれに従う）でレイアウト崩れ・意図しない横スクロール・要素の重なりがない
- ビューポート縮小時にコンテンツ・機能が失われない（1.4.10 Reflow 相当）

## 4. Worked Example: 「設定フォームに削除ボタンを追加する PR」

> 汎用題材の通し例。発火判定 → チェック → finding 化までの流れを示す。

### 4.1 対象差分（仮想）

```text
components/settings/SettingsForm.tsx   | 32 +++++++++++++++
styles/settings.css                    |  8 ++++
api/settings/delete.ts                 | 20 ++++++++++
```

### 4.2 発火判定

- `components/**` + `*.tsx` + `*.css` を含む → **レーン 5 発火**（§1.1）
- `api/settings/delete.ts` は非 UI だが、差分全体として UI 変更を含むため発火判定は変わらない

### 4.3 チェック（抜粋）

| チェック | 観察 | 判定 |
|---------|------|------|
| Nielsen 5（エラー防止）+ 3（主導権と自由） | 削除ボタン押下で即時削除・確認ダイアログなし・undo なし | **Fail** |
| Nielsen 4（一貫性と標準） | 既存の破壊的操作ボタンは赤 + ゴミ箱アイコンだが、本 PR は青 + テキストのみ | **Fail** |
| WCAG 2.5.8 Target Size | ボタン実測 20×20 CSS px・隣接ボタンと 2px 間隔 | **Fail** |
| WCAG フォーカス可視 | `:focus-visible` スタイルあり（既存共通スタイル継承） | Pass |
| WCAG 2.4.11 Focus Not Obscured | フォーム末尾のボタンが sticky フッターに隠れない（実測） | Pass |
| レスポンシブ | SP 幅でボタンがフォーム外にはみ出さない（スクリーンショット確認） | Pass |

### 4.4 finding 例（6 観点表への分類）

| 観点 | Finding | Severity | 対応 |
|------|---------|----------|------|
| 仕様準拠 | 破壊的操作（削除）に確認ステップ・undo がない（Nielsen 5/3 違反。データ損失導線） | major | 確認ダイアログ追加 or undo 提供 |
| コード品質 | 削除ボタンの色・アイコンが既存の破壊的操作パターンと不一致（Nielsen 4 / UI 一貫性→可読性） | minor | 既存 destructive ボタンコンポーネントを再利用 |
| コード品質 | タップターゲット 20×20 px（WCAG 2.5.8 Fail） | minor | 24×24 px 以上 or 間隔確保 |

visual evidence: before/after スクリーンショット（PC/SP 2 点）を
`evidence/verification/` に保存する（`acceptance-review` Skill の
「UI 変更時の visual evidence 規約」参照）。

## 5. Optional: Figma ↔ 実装の計測突合

> **環境に Figma MCP + Playwright MCP の両方がある場合のみの optional 手順**
> （必須にしない）。無い環境では本節をスキップしてよい（§1.3 の unavailable
> 記録は「視覚入力ゼロ」の場合のみ必要。スクリーンショット等の代替入力が
> あれば本節なしで Pass/Fail 判定できる）。

1. Figma MCP で対象 node の仕様（font-size / color / spacing / structure）を取得
2. Playwright MCP で実装側の computed style・スクリーンショットを採取
3. 両者を表形式で突合し、閾値超（例: 1px 超のずれ・色相違）を finding 化
4. 意図的な逸脱（実装都合・レスポンシブ調整）は「妥協点」として記録し、
   デザイン正本側の更新要否を明記する

## 6. visual regression の業界標準（V-1 evidence 規約との整合）

- **baseline（スクリーンショット基準画像）は Git 管理**し、**意図的な UI
  変更は同一 PR で baseline を更新**する（変更を明示的・レビュー可能にする）
- **コンポーネント単位のスクリーンショットを優先**（full-page は重要フローのみ）
- 動的コンテンツ（timestamp・アバター・乱数由来）は**マスク**し、
  **アニメーションは無効化**（例: Playwright の `animations: 'disabled'`）
- 実行は PR 時のみ（毎 commit ではない）。描画一貫性のため CI/Docker 等の
  固定環境を前提とする
